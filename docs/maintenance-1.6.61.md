# 1.6.61 유지보수 기록

이번 배치는 일반 유지보수 사항, 업데이트 네트워크, Web 라우팅, 스킬 디렉터리 탐색만 다룬다. 호스트 패치 정의, 기본 프롬프트, 권한 정책, 자동 재시작 동작은 바꾸지 않았다.

## #92: 잠금 게시, 해제, 마무리

- 옛 버전은 `open(wx)` 이후에야 메타데이터를 썼기 때문에, 두 단계 사이에 프로세스가 종료되면 빈 잠금이 남았다. 새 버전은 고유 소유자 기록을 먼저 완전히 쓴 뒤 같은 파일 시스템의 하드 링크로 호환 잠금을 원자적으로 게시한다. 디렉터리 게이트는 계속 새 버전 프로세스를 조율하고, 옛 버전도 `maintenance.lock` 을 볼 수 있다.
- 두 잠금 이름은 같은 inode 를 가리켜야 한다; 임의의 추가 하드 링크는 허용하지 않는다. 파일 시스템이 이 동작을 지원하지 않으면 중단하고 보고하며, 빈 파일 구간이 있는 구현으로 되돌아가지 않는다.
- 해제 실패 시 더 이상 디렉터리 게이트를 잃지 않는다. 제한된 재시도 후 경고를 보고한다; 이 프로세스가 이미 기록한 원래 해제 클로저만 다음 획득 전에 재시도할 수 있다. 다른 활성 프로세스, 미지 호스트, 무효 내용은 나이를 이유로 잠금을 빼앗기지 않는다.
- `LOCK_UNREADABLE` 과 `LOCK_LOST` 는 모두 쓰기를 중단하지만, 각각 읽기 장애와 명확한 기록 변경/누락을 뜻한다. 복구 동작도 소유자를 다시 확인해야 한다.
- 검증 커밋 완료 후의 정리 오류는 복구 디렉터리를 보존하고 명확한 경고를 반환하며, 더 이상 롤백을 잘못 트리거하지 않는다. 커밋 전 실패는 기존 트랜잭션 복구 방식을 따른다.
- 이미 존재하는 빈 잠금/손상 잠금은 소유자 사망을 증명하지 않으므로 계속 사용 중으로 보고한다. 자동 잠금 삭제 버튼은 추가하지 않았다.
- 공식 1.6.59 에는 30분 기준 잠금 선점 로직이 없다; 검증되지 않은 이 가정을 위해 하트비트 시스템을 추가하지 않는다.

## #106: 하위 경로 배포

패널은 실제 로드된 플러그인 스크립트 경로에서 마운트 지점을 식별한다; 그 증거를 쓸 수 없으면 동일 출처 페이지/base 경로를 쓴다. API, 새로고침, 환경 조회 등의 요청은 URL 해석을 공유하고, 외부 링크는 다시 쓰지 않으며, 자격 증명을 교차 출처 base 로 보내지 않는다. 루트 경로와 데스크톱 진입점은 호환을 유지한다.

## PR #99: 업데이트 채널

기여자가 제안한 업데이트 채널 UI 와 독립 설정 파일은 유지하고, 요청 격리와 SOCKS5 핸드셰이크를 다시 구현했다:

- 단일 비동기 요청은 자기 환경 스냅샷을 가지며, 다중 인스턴스가 서로 섞이지 않고, `process.env` 나 시스템 프록시를 쓰지 않는다.
- token 만 입력해도 기존 HTTP(S)_PROXY/NO_PROXY 를 상속한다; 비워 두는 것은 상속을 뜻하며 강제 직결이 아니다.
- GitHub token 은 API 호스트로만 보낸다; 호스트를 넘는 리다이렉트에서는 요청 헤더를 다시 만든다. 공개 상태는 token 이나 프록시 인증 정보를 되비추지 않는다.
- 로컬 자격 증명 파일은 원자적으로 쓰고 POSIX 권한은 0600 이다. 손상된 파일을 읽으면 오류를 내고 설정을 조용히 무시하지 않는다.
- SOCKS5 는 프록시 측 도메인 해석을 쓰고 선택적 사용자 이름/암호 인증을 지원한다; 협상 버전, 인증 방식, 길이를 검증하고 응답 캐시를 제한하며, TLS 검증, 다운로드 출처 제한, SHA256 검증을 유지한다.

## PR #103: 스킬 탐색

내장 프리셋은 호스트 기본 스킬 디렉터리를 쓰고 사용자 DSH 디렉터리를 중복 등록하지 않는다. 실제 호스트 provider 는 사용자 DSH/agents, 프로젝트 DSH/agents, bundled 등 다섯 종류 디렉터리를 검증하며 `disable-model-invocation` 을 유지한다. 사용자가 수정한 프리셋은 기존 보호 절차를 따르고 강제로 덮어쓰지 않는다.

## 설치와 경계

기본 설치기는 복구 트랜잭션을 만들기 전에 CLI 를 찾을 수 있는지 먼저 확인하며, 실패해도 profile 의존성을 먼저 옮기지 않는다. 이 진단이 서드파티 배포판의 실제 호환성 검증을 대신하지는 않는다.

#95 의 office-skills 유실/손상은 아직 정확한 근본 원인을 확보하지 못했다. 이번 배치는 실제 링크 대상 보호 테스트를 유지하지만, 보고자 현장이 이미 복구되었다고 간주하지 않는다. #89, PR #102, PR #113 은 계속 따로 처리한다; 서드파티 패키지 교체 게이트 우회, Cookie 포트 병합, HTTP header 상한 상향은 켜지 않았고 rc.5/alpha 호스트를 자동으로 검증 완료 처리하지도 않았다.

## 검수

로컬 최종 후보 패키지의 검수:

- macOS Node 전체: 405개 항목, 393 통과, 12개는 플랫폼/실행 환경에 따라 건너뜀, 실패 0.
- Windows 11 / 4090 Node 전체: 405개 항목, 380 통과, 25개 건너뜀, 실패 0. Mac 과 Windows 의 실제 Electron 잠금·링크 삭제 테스트는 각각 32개 항목이 통과했다(자식 프로세스 명시적 대기, 종료 코드와 비어 있지 않은 결과 대조).
- 패널 회귀: 25개 항목 통과, 실제 HTTP 하위 경로 요청도 실행; CJS 패키징, 포맷, 문서, TGZ smoke 검사 통과.
- Mac 은 격리 디렉터리에서 실제 공식 CLI + pnpm 으로 최초 설치, 업그레이드, 롤백, 재업그레이드, 설치 실패와 롤백 실패 복구를 수행; file/link 의존성과 외부 대상 파일 센티널은 보존되었다. 옛 설치 별칭 마이그레이션도 실제 CLI 로 검증했고 설정과 프롬프트 센티널은 유지되었다.
- 두 플랫폼의 실제 호스트 스킬 provider 에서 다섯 종류 디렉터리, 중복 없음, 모델 호출 금지 표식을 모두 검증했다.
- 실제 로컬 TLS 를 HTTP CONNECT / SOCKS5 로 전송해 인증 격리, 호스트 간 리다이렉트, 인증서 불일치 거부, 타임아웃, 아카이브 SHA256 을 검증했다; 시스템 신뢰 저장소나 사용자 프록시는 바꾸지 않았다.

건너뛴 항목은 통과로 치지 않는다; Windows/macOS 의 Electron 보충 테스트는 Node 집계와 따로 센다. 여기서 영향받은 사용자의 서드파티 배포판, 현장 office-skills 손상, 전체 GUI 세션이 복구되었다고 주장하지 않는다. 정식 DSH, 사용자 profile, 프록시는 테스트로 수정되지 않았다. 클라우드 검사와 릴리스 산출물은 병합/릴리스 후에 다시 대조해야 한다.


### Windows 4090 전체 절차의 알려진 제한

Electron 을 명시적으로 대기한 뒤에도 실제 설치 절차가 옛 버전 파일을 백업할 때 실패했다: Defender 가 `skills/redteam/unauth-exploit.md` 를 격리해 읽기가 `UNKNOWN` 을 반환했다. 이 PC 의 보호 기록에 있는 경로, 시간, 예외가 일치하며 검출 이름은 `Backdoor:PHP/Chopper.E!dha` 이고, 기록에는 격리 성공·미실행으로 남아 있다. 스캔 결과만으로 오탐 여부를 단정할 수는 없다.

이미 릴리스된 1.6.60 과 이번 후보 패키지의 해당 파일을 바이트 단위로 대조했고, 모두 8298 바이트이며 SHA256 은 `d70e456d4c0ae0a2b4c2e767dc5c3d0a3131af3be1dc4f3cdc6ed21a8dcd7129` 로 이번 배치에서 그 내용을 바꾸지 않았다. 이 증거가 #95 보고자의 현장 재현을 대신하지는 않는다.

통과를 얻으려고 Defender 를 끄거나 예외를 설정하거나 격리 파일을 복원하거나 스킬을 삭제하지 않았다. Windows Node 테스트와 Electron 잠금 테스트는 통과했지만 **4090 에서의 전체 업그레이드/롤백 검수는 통과하지 못했다**. 처음 PowerShell 드라이버가 낸 빈 로그와 종료 코드는 증거로 치지 않는다; GitHub 세 플랫폼의 설치 및 실제 런타임 검사는 이후 모두 통과했다. 유지보수자는 위 제한을 인지한 상태에서 명시적으로 릴리스를 요청했으므로 이번에는 이 범위로 배포하며, 4090 의 차단은 알려진 문제로 남기고 현장 복구를 주장하지 않는다.
