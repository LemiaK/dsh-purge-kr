# 업데이트 상태 잔여와 재시작 대기 판정(1.6.41)

## 근본 원인

옛 스케줄러는 `pendingVersion === runningVersion` 일 때만 재시작 대기 기록을 지웠다. 1.6.33 을 자동 설치한 뒤 곧바로 1.6.40 으로 업그레이드하면 1.6.33 기록이 영구히 남는다. 같은 옛 기록이 이후 자동 설치를 막기도 한다. 메타데이터 검사가 한 번 성공했다는 이유로 `hasUpdate=false` 일 때 설치 실패 안내를 숨긴 적도 있다.

## 현재의 증거

- 실행 버전: 모듈을 처음 로드할 때 고정되며, 프로세스가 도는 동안 디스크의 패키지 교체를 따라 바뀌지 않는다.
- 디스크 버전: 현재 profile 의 논리 경로 `node_modules/dsh-purge-community/package.json` 에서 읽는다. pnpm 옛 store 의 패키지를 현재 설치로 보지 않고 다른 profile 을 빌려 쓰지 않는다.
- 둘이 같음: 옛 `pendingVersion/restartRequired` 를 지운다. `lastPendingVersion`, `pendingResolution`, 설치 시각, 실패 대상 기록은 보존한다. 롤백된 낮은 버전을 로드한 경우에도 이미 지난 대기 상태를 해제할 수 있다.
- 둘이 다름: 실제 디스크 버전과 실행 버전을 표시하고 수동 재시작을 계속 기다린다. 업그레이드와 롤백 모두에 적용된다. 같은 로드 대기 버전의 다중 profile 부분 실패만 기존 수정 재시도 경로를 쓸 수 있으며, 그 때문에 다른 수동 롤백을 덮어쓰지 않는다.
- 버전 미지, 패키지 신원 오류, 파일 누락, 읽기 불가: 상태 대조 오류를 명확히 표시하고 자동 설치를 멈춘다. "복구됨"으로 처리하거나 옛 기록을 숨기지 않는다.
- 설치 실패와 검사 실패는 따로 보존한다. 네트워크 검사 성공, 새 버전 없음, 재시작 그 자체로는 실패 대상이 고쳐졌음을 증명하지 않는다. 설치 재시도가 성공해야 설치 오류를 지운다.

기동과 자동 검사가 상태를 마이그레이션한다. 유지보수 페이지 GET 은 같은 규칙으로 계산한 뷰만 반환하며 설정을 쓰거나 설치하지 않는다. 자동 검사/설치 스위치, 검사 간격, 프롬프트, 규칙, 권한, 다른 플러그인은 바뀌지 않는다. 패치를 자동 적용하거나 재시작하지 않는다.

## 옛 버전에 묶인 사용자

옛 프로세스는 새 스케줄러를 스스로 얻을 수 없다. 먼저 유지보수 페이지에서 정식판 1.6.41(또는 독립 설치기)을 수동 설치한다. 업데이트 스위치를 반복해서 켜고 끄지 말고 상태 디렉터리 전체를 삭제하지 않는다. 설치 후에도 사용자가 직접 DSH 를 한 번 종료하고 다시 열어야 한다. 옛 기록은 새 버전이 로드된 뒤 자동으로 대조해 처리한다. 롤백해도 기존 자동 업데이트 스위치는 바뀌지 않는다. 옛 버전에 오래 머물려면 이미 있는 버전 고정 옵션을 쓴다.

## 회귀 진입점

- `test/update-status.test.mjs`: 버전 전환, 재시작 대기, 롤백, 읽기 실패, 설치 실패, 동시 수동 패키지 교체.
- `test/update-policy.test.mjs` / `test/update-recovery.test.mjs`: 독립 스위치, 재시도, 다중 profile 부분 실패와 실패 복구.
- 패널 maintenance 테스트: 실행/디스크 버전 안내, 미지 상태, 네트워크와 설치 오류 동시 표시. 설치나 재시작을 트리거하지 않는다.
- `scripts/verify-rollback-runtime.mjs`: 실제 DSH CLI 로 패키지 설치, 롤백, 재업그레이드, 주입 실패 복구를 수행한다. 로드된 모듈을 유지하면서 pnpm 논리 설치 경로와 실행 버전을 함께 대조한다.

검수는 임시 profile 만 쓴다. 검증을 위해 사용자의 update-preferences.json, 프롬프트, 프록시를 바꾸거나 사용자 DSH 를 기동/종료하지 않는다.
