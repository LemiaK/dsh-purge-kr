# 1.6.48: 사용자 정의 본문 보호와 설치 별칭

## #72: 본문 귀속을 키워드로 추측할 수 없다

옛 버전은 본문에 세 개의 템플릿 표식이 모두 있으면 플러그인 기본값으로 간주했고, `customized: true` 조차 무시했다. 저장은 성공할 수 있었지만, 이후 시작 동기화나 적용이 사용자 정의 내용을 기본값으로 바꿀 수 있었다.

이 버전은 시작 동기화, 적용, 기본 설치 경로의 판정을 통일한다:

- 명시적으로 저장된 사용자 정의 내용은 보존한다. 템플릿 표식이 남아 있어도 귀속은 바뀌지 않는다.
- 상태 기록이 없거나, 상태가 손상되었거나, 수동 편집 후 출처를 확인할 수 없는 비어 있지 않은 본문은 보존한다.
- 현재 기본값, 그리고 `customized: false` 이면서 본문 지문이 기록과 정확히 일치하는 옛 기본값은 기존 로직대로 갱신한다.
- 본문 읽기에서 오류가 나면 쓰기를 중단하고 오류를 반환하며, 오류를 빈 파일로 취급하지 않는다.
- "기본값 복원"은 여전히 명시적 조작이며, 주입 위치, 강화 섹션, 호스트 패치, 기존 스위치를 바꾸지 않는다.

옛 버전이 이미 덮어쓴 본문은 자동으로 추론해 복구할 수 없다. 먼저 사용자가 직접 저장한 원고나 이 PC 의 백업을 확인하고, 확인된 본문만 복구하며, 설정 전체를 복원해 이후 변경을 덮어쓰지 않는다. 사용자에게 공개 issue 에 개인 프롬프트를 업로드하라고 요구하지 않는다. 출처를 확인할 수 없는 옛 기본값은 보존한다. 새 기본값을 정말 쓰려면 사용자가 직접 기본값 복원을 선택한다.

## #74: 의존성 이름과 패키지 신원을 따로 대조한다

`node_modules/dsh-purge-community` 와, 실제 `package.json.name` 이 `dsh-purge-community` 인 `node_modules/dsh-purge` 별칭을 지원한다. 현재 명시적으로 선택된 profile 만 검사하고 그 활성화된 bundle 을 우선한다. 실행 프로세스의 옛 버전으로 디스크 버전을 대신하지 않고, 다른 앱이나 전역 설치를 스캔하지 않는다.

패키지 누락, 신원/버전 불일치, 읽기 불가, 여러 개의 서로 다른 활성 사본은 여전히 오류로 보고한다. 두 개의 서로 다른 사본 중 명시적으로 선택된 것이 없어도 모호성으로 유지한다. 진짜 업스트림 `dsh-purge` 는 커뮤니티 버전으로 둔갑하지 않는다. 세 번째 사용자 정의 의존성 이름은 이번 자동 마이그레이션 지원 범위가 아니며, 의존성을 삭제하거나 버전을 위조해 오류를 없앨 수 없다.

YAML 파서는 검증된 패키지의 실제 물리 경로에서 해석하며 pnpm 격리 의존성 레이아웃을 커버한다. 백업은 의존성 이름과 실제 패키지명을 함께 기록한다. 롤백은 원래 의존성 이름으로 설치하고 해당 bundle 과 알려진 설정 참조를 복원하며, 프롬프트, 다른 설정, 백업 이후 사용자가 추가한 내용을 보존한다. 옛 백업 형식도 계속 읽을 수 있다.

옛 버전에 `reconciliationError` 가 있으면 자동 설치를 중단하므로, 스스로 업그레이드되기를 기다릴 수만은 없다. 새 버전 독립 설치기로 제자리 업그레이드하며, 제거, 잠금 파일 삭제, 상태 파일 비우기는 필요 없다. 설치 후 수동 재시작은 사용자가 정한다. 현재 프로세스는 여전히 옛 코드다. 1.6.47 이나 그 이전 버전으로 롤백하면 옛 본문 판정 결함도 함께 돌아오므로, 롤백이 끝났을 때 파일이 남아 있다는 것이 옛 버전이 다시 로드된 뒤에도 새 보호가 유지된다는 뜻은 아니다.

## 검증 방법과 경계

- `test/prompt-preservation.test.mjs`: 저장, 시작 동기화, 적용, 옛 기본값 마이그레이션, 상태 누락/손상, 수동 편집, 명시적 기본값 복원, 읽기 실패.
- `test/installed-package.test.mjs`: 표준 이름/별칭, pnpm 물리 경로 해석, 여러 사본, 선택된 진입점 누락, 패키지 신원 오류와 별칭 백업.
- `scripts/check-alias-install-runtime.mjs`: 명시적 Mac CLI 전용 사본 또는 실행 중이 아닌 Windows 테스트 사본과 새 home 을 쓰고, 실제 DSH CLI/pnpm 으로 두 이름을 설치하며, 자동 업그레이드, 수동 스냅샷 롤백, 재업그레이드, 설치 실패 복구, 롤백 실패 복구를 수행하고 사용자 데이터를 바이트 단위로 대조한다. Mac 은 시스템 쓰기 샌드박스를 상속하므로 정식 앱과 사용자 DSH 데이터에 쓰는 것은 금지된다.
- CI 의 `scripts/check-npm-alias-runtime.mjs` 는 독립 공식 npm 호스트에서 같은 시나리오를 재사용하며 프로덕션 profile 을 쓰지 않는다.

이 테스트는 데스크톱 앱을 기동하지 않고, 호스트 패치를 자동 적용하지 않고, 모델을 호출하지 않으며, 설치 통과를 모든 모델 동작 검증 완료로 표현하지 않는다.

## 릴리스 전 실제 기록

Mac 과 Windows 11 4090 의 격리 사본 모두 Electron 44.7.0 / Node 24.21.0 을 쓰고, 공식 DSH CLI/pnpm 으로 1.6.47 → 1.6.48 을 완료했으며, 두 설치 이름 모두 업그레이드, 롤백, 재업그레이드, 설치 실패 복구, 롤백 실패 복구, 본문 바이트 보존을 통과했다. Windows 에서 npm 공식 소스 접근 시 연결 리셋과 타임아웃이 발생해, 이후 이미 있던 의존성 캐시로 실제 설치를 완료했다. 이것은 그 기계의 온라인 다운로드 경로가 복구되었다는 뜻이 아니며 프록시는 바꾸지 않았다.

로컬 전체 회귀 360항목: 348 통과, 12항목은 다른 플랫폼에만 해당해 스킵, 실패 0. UI, 문서, 클라이언트 빌드 일관성, 패키징 smoke 모두 통과했다. 클라우드에서는 세 플랫폼 설치기와 공식 npm 호스트 테스트를 따로 실행하며, 최종 상태는 PR #75 점검 기록을 기준으로 한다.
